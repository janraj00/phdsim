# Offline counterfactual acquisition labels

Implemented on the SCOUT branch, 2026-11-11. This stage creates examples for
learning the value of observation requests. No learned policy or online
value-of-information planner is implemented yet.

## Run

From the SCOUT worktree with Python 3.11+ (standard library only):

```sh
PYTHONPATH=src python3 -m phdsim.cli scout \
  --config configs/scout/pilot.json --collect-labels \
  --seeds 42 43 44 45 46 --decision-ticks 0 8 16 \
  --max-candidates 6 --output runs/scout-labels-next
```

The tested desktop Python executable is
`/Users/janek/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3`.
The macOS system Python may be older than3.11. Use a fresh output directory.
`--policy uncertainty_scouting` selects that continuation/baseline trajectory;
by default the policy from the JSON config is retained (`no_scouting`).
`--collect-labels` and `--compare` are different modes and cannot be combined.

## What is compared

1. Run the configured baseline until a decision at or after the requested tick.
   A slower rover may be in transit at that exact tick; the actual checkpoint
   tick is recorded. Duplicate actual checkpoints and finished missions are
   explicitly skipped.
2. Pause **after** processing received messages and local sensing, **before**
   requesting information. Re-reading that checkpoint does not sense twice.
3. Generate candidate observations using only the immutable local view and
   publicly configured sensor, motion and link parameters.
4. Fork the full simulator once per action. Every copy retains the same world,
   belief, resources, request history, continuation-policy state, queued
   captures and undelivered measurements. The source mission is not mutated.
5. Force exactly one first action (including the no-new-request baseline),
   then let the same continuation policy and belief-only route planner finish
   every branch. Rover movement, capture and transmission still consume time.

Forking and hidden-world access are offline evaluator capabilities. The
acquisition policy receives neither the simulator nor fork results.

## Candidate generation

`decision/acquisition/candidates.py` always includes no new request. For an
available drone it proposes centers ahead on the current route, uncertain
route cells, and cells on heuristic alternative routes. Alternatives are
generated by blocking uncertain bottlenecks in a **copy of the local belief**;
the true map and the rover's actual belief are never modified.

The set is capped (default6 observation actions plus no-request). Candidate
ranking uses entropy and is a search heuristic, not an estimate of mission
value. It does not guarantee complete coverage or the best possible viewpoint.
When the drone is busy only the no-new-request action is offered, preserving
the existing request. Helper feasibility uses its last received position.

Features include footprint/target entropy, route coverage, estimated time until
the rover sees the target locally, earliest/latest delivery times, sensor
accuracy, payload size and reserved energy. Visibility estimates follow the
current route and are proxies, not knowledge of the rover's future trajectory.

## Meaning of a training label

The initial objective minimizes arrival time with a hard energy budget.
Successful mission cost is its arrival tick. Any failure has the same fixed
cost, by default `mission.time_budget + 1`; an override must exceed the entire
time budget. Failing early is therefore not rewarded as a fast mission.

`realized_gain_ticks = no_new_request_cost - candidate_cost`.

- Positive: this intervention improved this particular simulated outcome.
- Negative: it worsened the outcome.
- Zero: arrival/failure cost was unchanged. A request may still consume more
  energy; `extra_energy_reserved` records that separately. Energy is not
  silently added to the time reward with an arbitrary coefficient.

This is **realized**, policy-dependent supervision in one fixed hidden world
and noise realization. It is not expected value across possible worlds. In
particular, choosing each state's best action from these results is a hindsight
oracle, not an online policy performance result. The `policy` field inside a
branch outcome denotes the continuation policy after the forced first action.

The baseline skips only the new request at this checkpoint. It does not cancel
existing requests or forbid later requests by the continuation policy.

## Output contract and leakage boundary

`labels.jsonl` has four top-level fields:

| Field | Contents | Training role |
|---|---|---|
| `schema` | Format version | Metadata |
| `group` | World seed, actual decision tick, continuation policy | Provenance and grouped splits; not model inputs |
| `inputs` | Local decision view, candidate action and pre-query features | Permitted model inputs |
| `target` | Realized gain, extra energy, action execution/delivery and terminal outcome | Offline supervision/evaluation only |

Neither truth, a world seed, future observation values, terminal metrics nor
world hashes are put in `inputs`. All branches from a world seed must stay in
one split. Rows at different decision ticks in the same world are correlated;
do not randomly split rows into training and test data.

`summary.json` records the resolved config, candidate configuration, objective,
requested/actual checkpoints, skipped states, source/config hashes and clearly
named `offline_best_*` diagnostics. `report.md` lists all comparisons.

## First inspected diagnostic

`runs/scout-counterfactual-v0` contains104 label rows at15 decision states from
five world seeds42–46 and checkpoint ticks0/8/16. There are89 observation
actions and15 no-request baselines. Observation labels:5 positive,7 negative,
77 zero;43 rows propose a target originating from an alternative route.

For example, in seed45 at tick0, observing cell(16,24) reduces the simulated
arrival time by4 ticks. At tick16, observing(16,8) increases it by15 ticks.
These are inspected individual outcomes under noisy sensing and a fixed
continuation planner, not evidence of expected gains or a deployable policy.

Verification includes exact parity with all ten original complete mission
records; pause/resume equivalence; independent forks preserving captured but
undelivered payloads; candidate generation independent of truth; local-map
immutability; direct intervention/label agreement; busy helper constraints;
failure-cost semantics; slow-rover checkpoints; and CLI output validation.

## Next research step

Broaden the map families and collect independent world groups before training
a surrogate. Learn expected gain from local inputs across varied worlds and
noise, retain no-request as a real action, and evaluate on unseen worlds with
matched budgets. Current labels mostly have zero time gain, so a trivial
always-no-request baseline and explicit energy/tie handling are essential.
Belief-sampled online rollouts, learned policies, explicit waiting and
federation remain separate subsequent steps.
